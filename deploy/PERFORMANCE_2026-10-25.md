# 2026-10-25 线上压测与服务端优化

## 结论与边界

北京时间 21:57–22:03，对 `https://star.baobo.me` 的现有版本 `20261025.50` / rulesVersion 5 做两轮 GET 混合负载测试。五个档位共完成 2,214 次请求，阶段内均为 HTTP 200；最高档目标 100 请求/秒、在途上限 40，实际完成约 97 请求/秒，P95 282.7ms、P99 813.8ms，结束后健康检查正常。

这是当前数据量、单个发压客户端、每档约 12 秒的短时读负载结果。没有测出容量极限，也不能换算为同时在线玩家数或结算吞吐。网络时延包含在结果中；没有读取线上 CPU、内存、PostgreSQL 锁或连接指标。预检最初有一次连接失败（没有 HTTP 响应），随后预检和正式阶段正常，该失败不包含在阶段统计里。

本记录的基线测试完成时，优化代码仅在本地验证。下方线上档位之间的快慢差异来自同一线上版本，不能当作优化前后收益。生产写路径的并发测试使用本地 `pet_match_test`，不向线上成绩、图鉴、上传或通知系统写测试数据。获得上线授权后，发布后的原始样本与对照报告分别保存在本地 `data/performance/2026-10-25/online-after.json`、`online-after-report.md`。

## 根因与实现

1. **每日店长读取的锁与重复查询。** 原来每次读取都执行 BEGIN、同一天的 advisory lock、查询、COMMIT。现在先直接查询当天记录和实时上架状态，只有当天尚未选定或需要改选时才进入原有带锁事务，并在锁内重查。同一进程同一日期的在途请求共用一次读取，完成后立即释放，保留切日与下架改选行为。
2. **图片冷缓存击穿。** 同一图片并发缓存未命中时，原来会重复请求 R2/Slack、重复生成剪影和写磁盘。现在合并同组同键的在途读取，复用一次缓存/回源结果。每个请求仍先查实时上架或访问权限；照片权限判断在合并前执行，图片缓存头保持原样。
3. **重复结算占满连接池。** 原有数据库事务锁与结果哈希已保证只结算一次，但 40 个相同请求仍会各申请一个事务。现在按 `[gameId, playerId, payloadHash]` 合并在途提交；不同身份或内容各自进入原有冲突校验，数据库继续承担跨进程、重启和响应丢失重试的最终幂等。完成/失败后立即删除在途记录，后续重试重新读取数据库，保留竞猜奖励与宠物下架状态的更新。
4. **头像 TTL 被访问延长。** 原来图片文件的 mtime 既用于 TTL 又用于 LRU，每次命中刷新 mtime，常用头像可能永不过期。改为读取只在写入时更新的 `.type` 文件时间来判断 TTL，图片文件 mtime 继续负责 LRU。
5. **并发淘汰导致偶发 503。** 复核中用 3,000 字节缓存、40 个 100 字节图片错峰并发写入，稳定复现一轮淘汰删掉另一轮扫描中的文件，触发 `stat ENOENT`。现在同一缓存实例的淘汰串行执行，扫描容忍已经被淘汰或下架清理删除的文件；回归覆盖并发写入、容量限制与下架清理。

新增 `singleFlight` 只保存正在执行的 Promise，属于进程内请求合并，不是长期业务数据缓存。无需新增 Redis、数据库迁移或连接池扩容。排行榜本轮未发现查询瓶颈，继续实时读取。

## 本地对照

同一台机器、同一测试数据库夹具（6 只占位宠物）、同一 5 连接池，以 Fastify `inject` 测量，不包含公网网络。冷图片源用内存存储模拟 40ms 延迟、28KB 响应；结算事务注入 100ms 提交前等待，以制造真实并发重试窗口。每个场景单独比较，不用这些数值估计生产容量。

| 场景 | 旧实现 | 优化后最终复测 |
| --- | --- | --- |
| 店长：100 请求 / 20 并发，获取 DB 连接次数 | 100 | 5 |
| 店长：P95 | 12.1ms | 2.7ms |
| 店长：采样到的连接池等待峰值 | 15 | 0 |
| 冷图片：30 并发，源站请求次数 | 30 | 1 |
| 冷图片：P95 | 45.8ms | 44.1ms |
| 热图片：100 请求 / 20 并发，P95 | 5.0ms | 3.4ms |
| 同局重复结算：40 并发，获取 DB 连接次数 | 40 | 1 |
| 同局重复结算：采样到的连接池等待峰值 | 35 | 0 |
| 同局重复结算：P95（含注入的 100ms 等待） | 143.8ms | 112.0ms |
| 重复结算后的结果行数 / 累计局数 | 1 / 1 | 1 / 1 |

主要确定收益是减少回源、锁和事务数量；此前两次复测的店长 P95 为 2.8/3.2ms，重复提交数据库连接次数同样为 1，冷图回源次数同样为 1。热缓存图片 P95 在复测中出现过 6.4ms，微小延迟差异存在抖动，不宣称稳定提速。图片的每请求上架/权限查询仍保留，所以 30 个冷图请求仍各有一次数据库查询。

原始本地对照：`data/performance/2026-10-25/local-before.json`、`local-after.json`、`local-after-repeat.json`。最后缓存淘汰修复后的结果另存 `local-final.json`。

## 复跑与验证

本地并发基准会重建 **本地测试库**，应与服务端测试顺序运行，避免同时重置同一个测试 schema。在仓库根目录运行：

```sh
./server/node_modules/.bin/tsx server/scripts/benchmark-local.ts data/performance/local.json
```

线上读负载复跑，同样在仓库根目录运行：

```sh
node server/scripts/load-read.mjs --url https://star.baobo.me --rates 2,10,25,50,100 --seconds 12 --concurrency 40 --output data/performance/online.json
```

工具只发送预置路径的 GET，不跟随重定向。上限为 100 请求/秒、40 个在途请求、每档 60 秒、总计划 10,000 请求。收到 429、连续 3 次错误、至少 3 次且超过 5% 的错误，或完成至少 20 个请求后累计 P95 超过 2 秒，就停止新增压力并等待已发请求结束。正常阶段等待完整计划窗口，报告单独记录计划时长和排空时间。

服务端测试同时覆盖：在途成功/失败释放、不同请求键隔离、店长读取绕开选举锁、并发店长读取合并、冷图合并与下架拒绝、40 路重复提交只累计一次、TTL、并发淘汰及下架清缓存。原有结算冲突、事务失败回滚、跨应用实例重试、竞猜与权限用例继续执行。压测工具另有无网络单测，覆盖请求计数、在途上限、限流停止、连接失败和低速吞吐统计。

发布前检查命令（在 `server/`）：`npm test`、`npm run typecheck`、`npm run bundle`。本轮无 UI、引擎规则、数据库结构或部署配置修改。

最终验证：208 项 Vitest 用例与 5 项压测工具用例通过；服务端类型检查与 bundle 构建通过。独立复核发现的缓存淘汰竞态与低速阶段吞吐统计问题均已补回归并修复。
