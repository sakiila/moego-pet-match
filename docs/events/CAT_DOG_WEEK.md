# 猫派 vs 狗派周 · 设计方案与规则（草案）

日期：2026-10-27
状态：**草案，待用户确认**。确认后摘要写入 V1_RULES「阵营周」一节，流程写入 GAME_FLOW，文案写入 UI_COPY。

## 1. 一句话

为期一周的全公司阵营活动：同事报名「喵派」或「汪派」，每打完一局普通局，就按本局服务到的猫格、狗格为自己的阵营积分。首页拔河条实时显示双方差距，周一在 Slack 公布胜负。

## 2. 设计目标与边界

| 目标 | 做法 |
| --- | --- |
| 制造全公司话题 | 拔河条、每日战报、最后一天迷雾、Slack 开幕和收官贴 |
| 人人能贡献，不靠个别高手 | 每人每天只有前 5 局计分；看的是服务格数，不是分数 |
| 不打乱原有玩法 | 只改参战玩家的阵容抽样；引擎、计分、排行榜、图鉴和成绩校验一律不变 |
| 不增加作弊面 | 积分只取自服务端回放校验通过、已保存的结果 |
| 不刷屏 | Slack 一周最多 9 条：开幕 1、每日战报 7、收官 1 |

不做的事：实时对战、阵营聊天室、阵营专属排行奖励分、额外付费或兑换。

## 3. 活动时间

- 活动周：北京时间周一 00:00 到周日 24:00。对局按**登记日期 `board_date`** 归属，沿用现有每日同盘的规则。
- 报名：从开幕前一天起开放，活动期间随时可以加入，加入后开始计分，此前的对局不追溯。
- 收官：周一北京时间 10:00 发结果贴，对应美西周日 19:00。周一 00:00 后结算的局，只要登记日期在活动周内照样计分，所以收官前留 10 小时做最终统计。

## 4. 报名与阵营

- 两个阵营：**喵派 Team Meow**、**汪派 Team Woof**。
- 所有有效玩家都能报名，不要求自己养宠物。养鸟、养兔或不养宠物的同事自由选择。
- 报名页给出建议：自家上架宠物里猫多就推荐喵派，狗多就推荐汪派，但只是提示，不强制。
- **一周内不能换阵营**。报名前弹一次确认，提示「选定后本周不能更换」。
- 不报名的玩家照常游戏，不受任何影响，首页能看到拔河条和「加入」入口。

## 5. 阵容规则（只对已报名玩家生效）

活动周内，已报名玩家的普通局阵容固定为 **3 只猫 + 3 只狗**，双方面对的物种比例一致，积分只看手上功夫。

1. 先按原规则抽自家宠物（单宠 75%、多宠 65% / 20%，上限 2 只）。自家宠物占用对应物种的名额；如果自家宠物不是猫也不是狗，本周不入选。
2. 剩下的猫名额从非自家已上架的猫里抽，狗名额从狗里抽，各自沿用「未收集 2 : 已收集 1」和毛色降权。
3. 已上架的猫或狗不足 3 只时，用另一物种补满 6 种。补位后积分照常按物种计算。
4. 鱼关不变：鱼没有物种，不参与阵营积分。
5. 每日同盘的种子不变，棋盘形状和补落序列仍和全公司一致。

阵容属于服务端抽样，**引擎规则版本不变**。回放按 `games.lineup` 校验，不受影响。

## 6. 积分规则

**阵营积分以「服务格」为单位，不用游戏分数**，避免连消倍率和猜主人加分放大高手优势。

| 项目 | 规则 |
| --- | --- |
| 计分来源 | 已报名玩家在活动周内登记、正常到时、至少一次有效操作、保存成功的**普通局** |
| 单局积分 | 本阵营物种每被服务 1 格得 **2 分**，对方物种每格得 **1 分**；其他物种不计分 |
| 数据依据 | 结算结果 `pets[].served`（服务端回放已核对），配合宠物的物种归一化，沿用成就模块的猫/狗映射 |
| 每日封顶 | 每人每个北京自然日只计**前 5 局**合格对局，按结算顺序；第 6 局起照常玩、照常上排行榜，但不计阵营积分 |
| 不计分 | 鱼关、主动退出、零操作局、保存失败局；猜主人加分、催单奖励和游戏分数都不计入 |
| 幂等 | 每局最多计一次（以 `game_id` 为主键），重试保存不重复计分 |
| 离职或停用 | 已计的积分保留在阵营总分里，个人不再出现在阵营贡献榜 |

**人数平衡**：两边人数可能不均。阵营总分 = 成员积分之和 × 平衡系数。人少的一方系数 = min(1.3, 多方人数 ÷ 少方人数)，人多的一方为 1。系数按「至少计过 1 局的成员」统计，每天 00:00 更新并公示。这个设计既鼓励拉人，又让人少的一方有机会翻盘。

**胜负**：收官时调整后总分高的一方获胜。分差在 0.5% 以内判平局，双方都算胜方。

> 设计说明：本阵营物种计 2 分，让玩家有轻度策略可做（优先消自家物种），又不至于让对方物种的格子毫无价值、局内想太多。

## 7. 实时拉锯（首页）

- 首页开始营业按钮上方放一张活动卡：左侧喵派、右侧汪派，中间是拔河条，按双方调整后总分的占比来显示。
- 数据每 30 秒刷新一次（轮询，不加 WebSocket），首页打开时也会刷新。
- **领先易主**：当前领先方和上次查看时不同，拔河条中间弹一次「汪派反超！」。
- **最后 24 小时迷雾**：周日 00:00 起只显示「势均力敌 / 小幅领先 / 大幅领先」，不显示数字和精确比例，悬念留到收官。
- 卡片点开是阵营详情：双方总分、人数与平衡系数、今日贡献前 5 名、我的本周积分和今日剩余计分局数（例如「今日还可计 3 局」）。

## 8. 局内与报告

- 局内**不加**任何新的提示，棋盘信息层级保持现状。棋子底色不随物种改变。
- 报告页加一枚状态标签，并入现有标签行：「为喵派 +46」；当天已用完 5 局时显示「今日阵营积分已满，明天继续」。
- 报告的「店长说」随机提示池加 2 条阵营提示，只在活动周出现。

## 9. Slack 运营节奏

发在 #the-pet-corner。需要确认 Bot 有该频道的 `chat:write` 权限；目前 Bot 只用来私信 Bob。

| 时间（北京） | 内容 |
| --- | --- |
| 开幕前一天 18:00 | 开幕贴：规则三句话、报名链接（首页 Slack 预览卡）、上周对阵（如有） |
| 每天 10:00 | 战报：双方总分与差距、昨日阵营之星各 1 名、昨日被服务最多的猫和狗。周日改发迷雾版，不报数字 |
| 收官周一 10:00 | 结果贴：胜方、最终比分、双方贡献前 3、最努力的宠物，并 @ 胜方阵营之星 |

所有贴子由服务端定时任务生成，文案走 i18n 的英文版，因为频道是全员共用。发送失败只记日志、不重试刷屏，和现有上传通知的策略一致。

## 10. 奖励（不影响分数和排名）

| 奖励 | 条件 |
| --- | --- |
| 阵营冠军徽章「喵派冠军 · 2026 秋」或「汪派冠军 · 2026 秋」 | 胜方成员中至少计过 1 局的人 |
| 参战徽章「阵营周参战」 | 败方成员中至少计过 1 局的人 |
| 阵营之星徽章 | 每个阵营本周个人积分前 3 名 |

- 徽章沿用现有收集称号体系，可以佩戴到名片和排行榜。图标需要新做三枚，交给 Codex 生成，走图标库母版流程。
- 只报名、一局都没计过的成员不发奖。

## 11. 数据与接口（实现参考）

```sql
-- 一次活动
CREATE TABLE pet_match.faction_events (
  event_id text PRIMARY KEY,               -- 如 'catdog-2026-11'
  starts_on date NOT NULL, ends_on date NOT NULL,   -- 北京自然日，含首尾
  fog_from date,                           -- 迷雾起始日
  settled_at timestamptz                   -- 收官后写入，之后不再计分
);
-- 报名：一周一个阵营，不可更换
CREATE TABLE pet_match.faction_members (
  event_id text REFERENCES pet_match.faction_events,
  player_id text NOT NULL,
  faction text NOT NULL CHECK (faction IN ('cat', 'dog')),
  joined_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (event_id, player_id)
);
-- 每局贡献：在结算事务中写入，game_id 保证幂等
CREATE TABLE pet_match.faction_contributions (
  game_id uuid PRIMARY KEY REFERENCES pet_match.games,
  event_id text NOT NULL, player_id text NOT NULL, faction text NOT NULL,
  board_date date NOT NULL,
  own_cells int NOT NULL, other_cells int NOT NULL,
  points int NOT NULL,                     -- 超出每日封顶的局写 0，保留记录便于核对
  created_at timestamptz NOT NULL DEFAULT now()
);
```

- 开局：`games` 登记时如果玩家已报名、且登记日在活动周内，就改用 3 + 3 抽样（`lineup.ts` 增加物种配额参数，补单元测试）。
- 结算：在现有结算事务里按玩家加锁，统计当天已计局数，再写入贡献记录（补单元测试：封顶、幂等、跨零点、鱼关、零操作）。
- `GET /api/faction`：双方总分、人数、系数、迷雾状态、我的阵营和今日剩余计分局数，服务端缓存 30 秒。
- `POST /api/faction/join`：要求已登录会话；重复报名同一阵营幂等，改报另一阵营返回 409。
- 定时任务：每日战报、收官结算（写 `settled_at`、发徽章、发结果贴），用命令行脚本 `server/scripts/faction.ts preview|post` 预览后再发，跟其他运维脚本一样默认只预览。
- 组件：`FactionTugBar`、`FactionCard`、`FactionJoinSheet`、`FactionDetail`，每个组件都登记到陈列页，状态包括未报名、已报名、迷雾、平局、已收官、加载失败、长英文名、中英文。

## 12. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 一方人数远多于另一方 | 平衡系数（上限 1.3）；开幕贴里展示双方人数，引导大家选人少的一边 |
| 少数人狂刷 | 每日只计 5 局，个人上限约为普通玩家的 1–2 倍 |
| 时差导致海外同事吃亏 | 按天封顶而不是按时段；收官前留 10 小时补登记 |
| 一边大比分领先后大家没兴趣 | 平衡系数 + 最后 24 小时迷雾 |
| 猫或狗素材不足 3 只 | 用另一物种补满，积分仍按物种算 |
| Slack 刷屏 | 每天只发一条，所有贴子都要先预览 |
